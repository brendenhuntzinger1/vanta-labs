## Affiliate / ambassador system (Vanta Labs website)

An ambassador is TWO rows in two unrelated tables that share an `id` by convention only — there is no FK between `partners` and `ambassadors`, and no DB trigger keeping them in sync. Every sync is application-level. Split of authority (verified by reading both sides, not the comments): - MONEY / PRICING reads `ambassadors`: `validateReferralCode` (quote-order.ts:262), `ensureCommissionRecord` (payment-webhook.ts:629), `getEffectiveCommissionPercent`, `isApprovedAmbassadorCustomer`, the anon `validate_referral_code` RPC, and `autoApproveEligibleCommissions`' status gate. - IDENTITY / ROSTER / PAYOUT-RELEASE reads `partners`: `getPartnerByAuthUserId`, `getApprovedPartnerByAuthUserId` (gates the ambassador dashboard), `getAdminPartnerRows` (base rows), `getPartnerSummary` (name, code, status, payout handle), `markCommissionsPaid`'s approval gate, `getPayoutQueue`'s `onHold`, and both `admin-ambassadors.ts` name lookups. - `fetchAuthoritativeRates` (partner-portal.ts:1059) patches ambassadors' rates over partners rows for display, but returns an EMPTY MAP on any error, silently reverting to the partners copy. Referral entry `/r/[code]` resolves through `resolveReferralCode`, which tries `ambassadors` then falls back to `partners` then aliases — a wider resolver than checkout's, so a partners-only code attributes a click and sets the cookie but is dropped at checkout. The cookie (`vl_referral_code`, 30d, non-httpOnly) is never read server-side; `create-session` uses `body.referralCode` only. cart-context hydrates the cookie into the visible field, so link auto-apply and manual entry converge on one server path. `minimum_qualifying_order` is enforced on BOTH paths and at both layers: `quoteOrder` throws below it (line 566), `ensureCommissionRecord` re-checks with the pre-discount `qualifyingSubtotal` (line 667), and the cart suppresses the referral candidate client-side. Commission ledger is duplicated: `referral_orders` (authoritative, all aggregations) mirrored to `commissions`. Payouts duplicated: `partner_payouts` mirrored to `payouts`. Every mirror write is a separate, unguarded statement. Only the payout queue was converted to server-side aggregation (`affiliate_balances`); the ambassador's own dashboard, program stats, refunded counts and the fraud queue still do unbounded PostgREST selects with JS reduce.

```

## Email system (Vanta Labs Next.js storefront, website/)

Every app-sent email funnels through one function, `sendEmail()` (src/lib/email/send.ts), which resolves a provider per-call from admin-editable settings layered over env (src/lib/email/settings.ts → getEmailRuntimeConfig). Email is DISABLED by default; disabled returns `NoopEmailProvider`, which reports `success:false` — so every caller sees a failure, not a no-op. Providers: nodemailer SMTP (checks `info.accepted`/`rejected`), Resend (honours `Idempotency-Key`), SendGrid (no idempotency), noop. `sendEmail` never throws. Three wrappers sit above it: - `sendOrderEmailOnce()` (order-email-once.ts) — claims a row in `order_email_log` BEFORE sending, protected by a partial unique index on `(order_id, kind) where status in ('sending','sent')`, and passes `idempotencyKey = "${kind}:${orderId}"`. Only used for `order_confirmation`; `refund_confirmation` is a declared kind with no caller. - `sendMarketingEmail()` (marketing.ts) — checks `email_suppressions`, appends the HMAC unsubscribe footer, may use a separate marketing From, then best-effort logs `email_send_log` with a status. - `enqueueFailedEmail`/`retryPendingEmails` (retry-queue.ts) — durable transactional retry via `pending_emails`, drained by the cron sweep. There is a fourth, entirely separate channel: Supabase Auth's own SMTP (`signInWithOtp`, `resetPasswordForEmail`, `admin.inviteUserByEmail`), invisible to all of the above — which is why `emailVerificationTemplate`/`passwordResetTemplate` exist but have no caller. `/api/cron/sweep` (every 30 min, `vercel.json`) drives four email jobs: `retryPendingEmails`, `runAbandonedCartSweep`, `runCampaignSweep`, `runAutomationSweep`, plus `runMembershipBillingSweep`'s five reminder/receipt stages. Dedupe is per-subsystem and inconsistent: DB unique index (order_email_log, abandoned_cart_emails, email_campaign_recipients), read-then-write against `email_send_log` (automations, coupon broadcast), atomic column claim (`paid_side_effects_at`, `renewal_reminder_sent_at`), or nothing at all (admin resends, shipping emails, refund confirmation, commission-earned, membership receipts). Roughly two-thirds of send sites use bare `sendEmail` inside an empty `catch {}` and discard the result — those fail completely silently.

## Fulfillment, shipping and Shippo integration (Vanta Labs website)

Vanta self-fulfils. The canonical fulfillment state machine is PURE and lives in `src/lib/order-pipeline.ts` (12 statuses, a 9-step `PIPELINE_PROGRESSION` ladder plus 3 unranked exception statuses, a per-status source allow-list, an explicit edge table, terminal protection and a rank-based no-regression rule that applies ONLY when `source === "shippo"`). Every shipping write is supposed to route through `applyTransition()`/`canTransition()` — and in this subsystem they genuinely do (`service.purchaseLabelForOrder`, `service.applyTrackingUpdate`, `service.setOrderFulfillmentStatus`, `order-sync.applyTransactionCreated`). I verified each call site rather than trusting the comments. Two inbound Shippo paths exist. `track_updated` → `service.applyTrackingUpdate()` is authenticated (required `SHIPPO_WEBHOOK_SECRET`, header or `?secret=`, SHA-256 + `timingSafeEqual`, fails closed with 503) and deduped by inserting `shippo_webhook_events.event_key = "<transaction|tracking>:<status>:<status_date>"`, catching 23505. `transaction_created` → `order-sync.applyTransactionCreated()` shares the same auth but has **no dedupe** — the route calls the handler first and only afterwards `upsert`s the event row, so every redelivery re-runs the whole write. Labels are normally bought by hand in Shippo's dashboard; Vanta's own purchase path is gated off by default (`SHIPPO_ALLOW_LABEL_PURCHASE !== "true"` → `purchasing_disabled`). When enabled it is protected by four layers: already-bought short-circuit, an atomic `label_purchase_claimed_at` claim, a `Shippo-Idempotency-Key` keyed on the order, and claim-retention on any ambiguous failure. Parcel weight is computed purely in `src/lib/shippo/parcel.ts`: order override → (preset tare added once) + Σ(unit weight × qty). Unit weight = dose weight → product weight → liquid fallback → 0.36 oz dry-vial default. A liquid is detected ONLY by parsing `product_doses.label` for an mL quantity; there is a physical-impossibility floor that rewrites a stored weight ≤ the mass of the fluid alone. The admin workstation (`/admin/fulfillment/workstation`) is a read-only derived view: buckets and exceptions are recomputed from `orders` on every load, batches are pure grouping, and no GET in the label routes can spend money.

## Inventory & Catalog (Vanta Labs storefront)

Two tables hold the catalog: `products` (parent) and `product_doses` (dose/size variants, FK product_id). **The sellable unit is the dose whenever the product has at least one `is_enabled` dose; the parent row is the shelf only for an undosed product.** The cart-line id and `order_items.product_id` encode this as a string: `"<slug>"` or `"<slug>::<doseUUID>"`, split back apart by `parseOrderItemRef` (inventory-fulfillment.ts:33), which is what decides WHICH ROW inventory moves on. Storefront availability is computed in `src/lib/catalog.ts`. `fetchProductRelations` loads enabled doses plus `reserved_quantity` from both tables (`fetchReservedQuantities`, catalog.ts:95 — wrapped in a bare try/catch that degrades to "nothing reserved"). Per row: `sellable = max(0, inventory_quantity - reserved_quantity)`, then `publishableAvailability` clamps to `MAX_UNITS_PER_ORDER_LINE` (10) before serialization. `resolveStockStatus(rawStatus, inventoryActive, quantity)` (catalog.ts:32) returns "In Stock" for everything when tracking is off; with tracking on, quantity <= 0 forces "Out of Stock", otherwise the stored `stock_status` string wins. `mapProductRow` sets the product's headline status/availability from the **default dose only** (`doses.find(isDefault) ?? doses[0]`), falling back to the parent row when there are no doses — so `products.inventory_quantity` is correctly bypassed for dosed products *in catalog.ts*, but not everywhere else (see riskAreas). **Two independent flags gate stock, and they are not the same flag.** Global `inventory.tracking_enabled` (admin_control section `inventory`, default false, fail-open false — `lib/inventory-settings.ts`) gates *display* and `/api/cart/validate`. Per-row `track_inventory` (boolean, default false) gates *enforcement* inside the `reserve_inventory` SQL and inside `getStockLevelsBySlugs`. No application code ever writes `track_inventory`; only the `inventory-enforce-positive-stock.sql` backfill does. Reservations are taken at order creation (never add-to-cart): `payment-service.ts:291` for card+manual, `express/authorize/route.ts:316` for Apple Pay. `reserve_inventory()` is one row-locked conditional UPDATE per line, idempotent on `(order_id, slug, coalesce(variant_id,''))`. TTL 15 min card / 24h manual. Decrement on payment is `finalize_inventory_for_order()`; the legacy `adjust_inventory_on_sale()` is the fallback behind `if (fin.degraded || fin.finalized === 0)`. Release happens on decline/duplicate/refund/cancel and via `expire_stale_reservations()` from the 30-minute cron sweep.

**State machine**

```
inventory_reservations.status: 'active' → 'finalized' | 'released'. ## Discounts, coupons, promotions, bulk/BOGO offers, and memberships (Vanta Labs / website)

TWO resolvers, not one. The server's authoritative discount is `resolveCustomerDiscount` (src/lib/profit-engine.ts:152), called exactly once from `quoteOrder` (src/lib/quote-order.ts:613). Every server lane funnels through quoteOrder — card checkout (payment-service.createCheckoutSession:80), express session, express authorize, express shipping-rates — so the server side genuinely has one rulebook. The client's is `resolveCartDiscount` (src/lib/discount-resolution.ts:69), called once from cart-context.tsx:759; cart page, cart drawer and checkout page all consume `discountAmount` from that context, so the client also has one. But they are DIFFERENT FUNCTIONS with hand-mirrored rules. discount-resolution.ts's own header admits the "shared resolver" claim is false. Rule shape (both sides): ONE discount wins, greatest-savings. Candidates: bulk_savings, member_pricing, ambassador_personal, coupon, and a `promo` slot holding either buy3get1 OR referral (bundle suppresses referral outright — server `!isBundle && hasReferral`, profit-engine.ts:181). Quantity "Bundle & Save" pricing is baked into `subtotal`; every candidate is scored on what it saves BEYOND that via `compete(raw − quantityBundleSavings)`, so bundle pricing competes rather than stacks (unless admin `bundleStacking`). Percentages are computed on `fullSubtotal` (pre-bundle list), never on bundled prices. Stacking/exclusions: coupon+referral and coupon+B3G1 both HARD THROW server-side when `couponPolicy.allowStacking` is false (quote-order.ts:559,562) — the production default. With stacking ON the server ADDS the coupon on top of the best promo (profit-engine.ts:213); the cart has no such branch at all. Referral is exclusive of store credit and points on both sides. Referral requires `minimumQualifyingOrder` ($100 default) or the server throws. Membership: perks resolve through `getMembershipPerks` (membership.ts:190) gated by `isMembershipActive` (membership-status.ts:51, 3-day grace). Paying grants membership ONLY through the Veyra recurring lane: /api/membership/subscribe → `startMembershipSignup` (membership-billing.ts:526) → `startVeyraMembership` → on charge success upsert `customer_memberships` active with `veyra_membership_id`. Renewals arrive only as `membership.renewed` webhooks (membership-webhook.ts:141); `runMembershipBillingSweep` deliberately skips every row with a veyra_membership_id. `activatePaidMembership` (webhook-driven) still exists but nothing in the app creates an `order_type='membership'` row any more — `createMembershipCheckoutSession` and `createAnnualMembershipManualOrder` have zero callers.

## Background jobs (cron sweep), analytics/ad pixels & conversion APIs, and configuration/environment fallbacks

PART A — JOBS. There is exactly ONE scheduler: `website/vercel.json` declares a single cron, `/api/cron/sweep` at `*/30 * * * *`. `src/app/api/cron/sweep/route.ts` (GET, `maxDuration = 60`, `dynamic="force-dynamic"`) authorizes with a constant-time compare of `Authorization: Bearer ${process.env.CRON_SECRET}` (401 if CRON_SECRET is unset — the sweep then never runs at all). It fans 13 jobs out of a keyed `JOBS` object CONCURRENTLY via `Promise.allSettled`, then records ONE `recordSystemAlert({type:"cron_sweep_failed", severity:"critical"})` if any promise rejected. Jobs that return an errors[] instead of throwing (`runCampaignSweep`, `runAutomationSweep`) never alert; a whole-function timeout/kill alerts nothing; and no last-successful-run timestamp is persisted anywhere — `system-status.ts:152-165` proxies "jobs are running" purely from `CRON_SECRET` being set. Idempotency quality varies sharply per job: real atomic claims exist in cart recovery (unique `(abandoned_cart_id, stage)` insert-before-send), campaign sending (`claimBatch` conditional UPDATE), payment reconcile (deterministic `reconcile-${orderId}` webhook event id feeding the real `processPaymentWebhook` claim chain), and membership reminder steps 1 & 4. They are ABSENT in `retryPendingEmails` (select-then-send, no claim), membership billing steps 2/3/5, and `autoApproveEligibleCommissions`. Row bounds are equally uneven: reconcile pages newest-first (10×50), Shippo sweeps cap at 20 oldest-first, campaigns/automations cap at 25/50, but membership billing, store credit, cart recovery, commission approval, express-intent expiry and the `expire_stale_reservations()` PL/pgSQL loop are all UNBOUNDED. `runAutomationSweep` additionally pages the ENTIRE orders table and the ENTIRE auth user list on every 30-minute tick. PART B — ANALYTICS. Three browser pixels (TikTok `ttq`, Snap `snaptr`, Reddit `rdt`) plus Vercel Analytics plus first-party `/api/analytics/track`, all gated on `localStorage["vl_cookie_consent"] === "accepted"`. Two server-side conversion APIs: TikTok Events API and Reddit Conversions API v3. There is NO Meta/Facebook pixel and NO Snap Conversions API server leg. Purchase has exactly one authority: `GET /api/ads/purchase-event/[orderId]`, which reads `payment_status`/`amount_paid` off the order and returns null unless `payment_status === "paid"` and a positive amount settled. It sends the TikTok and Reddit server legs as a side effect of the GET and returns the browser payloads in the same response. PART C — CONFIG. Business constants resolve through `getControlSnapshot()` (append-only rows in `admin_audit_logs`, read via the `admin_control_current` view with a 1500-row history fallback). Every reader swallows failure and returns a coded default, and the blank/NaN handling is inconsistent between readers.

**State machine**

```
Order payment_status (relevant to jobs + ads): pending_payment → paid (webhook `payment.succeeded`, or express reconcile feeding a synthetic signed event) | → payment_failed (reconcile sees failed|expired|canceled|cancelled at Veyra; releases inventory) ; paid → partially_refunded (stays reportable as "paid" upstream) → refunded | canceled. Only `payment_status === "paid"` (exact string, lowercased) unlocks an ad Purchase; the canonical predicate isPaidOrderStatus() in src/lib/ledger.ts also accepts "completed"/"succeeded", so the two disagree. Side-effect exactly-once is a separate latch: orders.paid_side_effects_at NULL→now, claimed independently of the paid flip so a crash between them re-runs safely. Membership: trialing/intro_status=active → (remainder charge succeeds) → active/intro_status=converted → (renewal charge) active → cancel_at_period_end=true → (next_billing_at passes) cancelled. Rows with veyra_membership_id NOT NULL are excluded from every step — Veyra owns their schedule. Campaign recipient: pending → claiming (conditional UPDATE) → sent | suppressed | pending (retry, attempts<3) | failed (attempts>=3); stale 'claiming' older than 10 min is reclaimed to pending or force-failed. Ad purchase ledger: absent → present (one row, PK order_id, written only on the TikTok branch); there is no per-platform state and `attempts` never increments.

## Admin surface, authentication, authorization & security posture (Vanta Labs Next.js storefront, website/)

Three independent identity systems coexist. (1) ADMIN: a bespoke username+password+6-digit-passcode system in `admin_credentials`/`admin_sessions`/`admin_login_attempts`, entirely separate from Supabase Auth. `/vault` is the login page; `POST /api/admin/auth/login` checks a DB-backed lockout (6 failures/15min per username OR per IP), scrypt-verifies the password, then a scrypt passcode (per-account `passcode_hash`, else `ADMIN_ACCESS_CODE`; `not_configured` is ALLOWED only when no second factor exists anywhere). Success mints 32 random bytes, stores sha256 in `admin_sessions` (12h TTL) and sets `vl_admin_session` (httpOnly, SameSite=strict, no maxAge). Every admin API route proves admin by calling `verifyAdminSessionFromRequest(request)` (or `...FromCookie()`), which re-reads `admin_credentials.role`/`is_active` per request and fails closed on error. RBAC is a 3-role matrix (`staff|manager|super_admin`) in `admin-roles.ts`; `normalizeAdminRole` defaults any unknown value to `staff`. (2) CUSTOMER: Supabase Auth driven entirely from the browser with the anon key (signUp/signInWithPassword/OTP/resetPasswordForEmail, optional Turnstile), then the access token is POSTed to `/api/auth/session`, which validates it with `auth.getUser()` and sets httpOnly `vl_session_token` (SameSite=lax, 30d if rememberMe). Server code re-validates on every call via `getAuthenticatedUser()`. Role comes from `detectRoleFromUser` — `admin` honored only from `app_metadata`, `partner`/`ambassador` accepted from either metadata as a non-privileged hint, everything else defaults to `customer`. (3) PARTNER/AMBASSADOR: no separate credential; authorization is `partners.auth_user_id == user.id AND status == 'approved'` via `getApprovedPartnerByAuthUserId`. `middleware.ts` is NOT an auth boundary — it only sets security headers, does an Origin-based CSRF check on state-changing `/api/{admin,account,membership,partner}`, and gates maintenance mode (with its own duplicate admin-session verifier). Page protection lives in `src/app/admin/layout.tsx` and `src/app/account/(dashboard)/layout.tsx`. The service-role key is confined to `supabase-server.ts` (`import "server-only"`) plus middleware and node scripts; no client bundle can reach it. All 75 admin routes carry the session check; 15 carry no role gate. Mock-payment surfaces are hard-disabled by `NODE_ENV === "production"` plus `isMockPaymentMode()`.

**State machine**

```
ADMIN SESSION: none → (POST /api/admin/auth/login: lockout OK + password OK + passcode ok|not_configured-and-nothing-provisioned) → active (row in admin_sessions, expires_at = now+12h, cookie vl_admin_session). active → active' on every verifyAdminSessionToken (last_seen_at touched; role/is_active re-read). active → revoked by: POST /api/admin/auth/logout (destroyAdminSession by token_hash); setAdminPassword (deletes ALL sessions for the username); updateAdminAccount({isActive:false}) (deletes all sessions); verifyAdminSessionToken finding the credential missing or is_active===false (deletes all sessions, returns null); expires_at passing. renameAdminAccount MOVES sessions to the new username rather than revoking them. Middleware caches session validity for 30s, so revocation can lag the maintenance-page bypass by up to 30s. ADMIN LOGIN LOCKOUT: open → (≥6 rows in admin_login_attempts with success=false in the trailing 15 min, counted as max(byUsername, byIP)) → locked (429 + Retry-After) → open again 15 min after the LATEST failed attempt. A successful login inserts a success=true row and does not clear the failures. ADMIN PASSCODE: not_configured (no account passcode, no ADMIN_ACCESS_CODE) → login allowed only while isAnyAdminSecondFactorProvisioned() is false for the whole system; once ANY account has passcode_hash or a valid 6-digit ADMIN_ACCESS_CODE exists, not_configured → 403 'needs its 6-digit login code set'. ADMIN ROLE: staff → manager → super_admin (strict superset); any unrecognised DB value normalises to staff. CUSTOMER SESSION: anonymous → (supabase.auth.* in browser) supabase-session → (POST /api/auth/session) app-session (vl_session_token) → signed out by DELETE /api/auth/session (server-side token revocation + cookie clear). ## Database schema, migrations, and integrity (repository side) — Vanta Labs Next.js storefront

There is no migrations directory and no migration framework. All SQL lives as 119 loose, unnumbered files in `/home/user/vanta-labs/website/src/lib/sql/`, applied by hand-pasting into the Supabase SQL editor. Nothing records what has been applied; ordering is implied only by prose in two documents that contradict each other (`DEPLOY.md` says run `deploy-run-once.sql` alone and claims it "bundles everything"; `DATABASE.md` Appendix C lists an 18-step order covering ~30 of the 119 files). Neither is complete: `deploy-run-once.sql` creates 43 of the 82 distinct tables the repo defines and only 3 of the ~19 application functions — it omits `inventory_reservations`, `order_attribution`, `coa_records`, the 13 `ad_*` tables, `express_*`, `shippo_*`, `referral_code_*`, `pending_emails`, `system_alerts`, `store_credit_ledger`, `inventory_transactions`, and every inventory-reservation, partner-application, affiliate-balance and admin-rollup RPC. `schema-complete-sync.sql` ("Creates every table, column, and index the app uses") omits `ambassadors` entirely. Because every file is `create table if not exists`, the FIRST file run wins and later files silently no-op. The same table has materially different definitions across files. `deploy-run-once.sql` and `schema-complete-sync.sql` declare **zero foreign keys**; `partner-system-repair.sql`, `affiliate-program-schema.sql`, `partner-portal-schema.sql` and `orders-schema.sql` declare them. `ambassadors.referral_code` is `text not null unique` in `partner-system-repair.sql` but plain nullable `text` in `deploy-run-once.sql`. So whether the affiliate system has referential integrity or unique referral codes depends entirely on which file someone pasted first. The affiliate domain is deliberately doubled: `partners`↔`ambassadors` are twin rows sharing one id (ambassadors is authoritative for money, partners for display), `referral_orders`↔`commissions` are a ledger and its mirror, `partner_payouts`↔`payouts` are a payout and its mirror, `partner_clicks`↔`referrals` both record clicks. Every one of these pairs is kept in sync by sequential PostgREST calls in application code, never a transaction — the sole exception being `create_partner_application`, a plpgsql function added after a production orphan defect. `ambassador_wallet_ledger` is referenced in the audit doc as existing live but appears nowhere in the repo. Percentages are whole numbers in `numeric(5,2)` (17.5 = 17.5%, divided by 100 at use). Money is split: order totals are `numeric(12,2)` dollars, while catalog prices, costs, postage, membership and store credit are `integer` cents — both live on `orders` (`discount_amount` dollars beside `store_credit_redeemed_cents`).
